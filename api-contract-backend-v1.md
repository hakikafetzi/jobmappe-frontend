## 1. Conventions

| Topic            | Rule                                                                                                                                             |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| Base URL         | `/api`. Local development: `http://localhost:8080/api`. Host and port MUST be configurable.                                                      |
| Authentication   | None.                                                                                                                                            |
| Media type       | Request and response bodies are JSON. Requests with a body MUST send `Content-Type: application/json`.                                           |
| IDs              | UUID strings, generated by the server.                                                                                                           |
| Dates            | `LocalDate` = ISO 8601 date, e.g. `"2026-10-03"`.                                                                                                |
| Timestamps       | `LocalDateTime` = ISO 8601 date-time **without offset**, server local time, may contain fractional seconds, e.g. `"2026-10-03T14:30:00.123456"`. |
| Response nulls   | Every field of a response type is always present. Fields typed `… \| null` are `null` when no value is set.                                      |
| Request fields   | Fields marked `?` may be omitted. Omitted and `null` are equivalent unless stated otherwise.                                                     |
| Text trimming    | Where noted, the server trims leading/trailing whitespace before validation and storage.                                                         |
| `201 Created`    | The body contains the created resource; the `Location` header contains its absolute URL.                                                         |
| `204 No Content` | No body.                                                                                                                                         |

Shared TypeScript aliases used throughout this document:

```ts
type UUID = string
type LocalDate = string // "YYYY-MM-DD"
type LocalDateTime = string // "YYYY-MM-DDTHH:mm:ss[.ffffff]", no offset
```

## 2. Errors

All error responses use the Problem Details format (RFC 9457, `Content-Type: application/problem+json`). The response may contain further standard fields (`type`, `instance`); the frontend MUST rely only on the following:

```ts
type ApiProblem = {
  status: number
  title: string
  detail: string
  errors?: Record<string, string[]> // only when title === "Validation failed"
}
```

### 2.1 Error catalog

| Status | `title`                       | Cause                                                                                                                              |
| ------ | ----------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| 400    | `Validation failed`           | One or more body fields violate a constraint. `errors` maps the request field name to its messages.                                |
| 400    | `Invalid sort property`       | A `sort` parameter names an unknown property (section 3.2).                                                                        |
| 400    | `Invalid request combination` | Query parameters that must not be combined were sent together (section 3.3).                                                       |
| 400    | `Bad Request`                 | Malformed JSON, missing body, wrong value type or unknown enum value in the body; invalid UUID or enum value in the path or query. |
| 404    | `Resource not found`          | A resource addressed in the path or referenced in the body does not exist.                                                         |
| 404    | `Not Found`                   | The URL does not match any endpoint. This is a client bug.                                                                         |
| 405    | `Method Not Allowed`          | The path exists, but not for this HTTP method. This is a client bug.                                                               |
| 409    | `Conflict`                    | The request is valid but violates a business rule or a uniqueness constraint (see the endpoints).                                  |
| 415    | `Unsupported Media Type`      | Missing or wrong `Content-Type` on a request with a body. This is a client bug.                                                    |
| 500    | `Internal server error`       | Unexpected server error.                                                                                                           |

Rules:

- The frontend MUST distinguish error cases by `status` and `title` only. It MUST NOT parse `detail`.
- `detail` of a `409` is a human-readable English sentence and MAY be shown to the user.
- A `409` raised by a concurrent write (e.g. two requests creating the same company name at once) has the generic detail `"The request conflicts with existing data."`.

### 2.2 Validation example

```json
{
  "type": "about:blank",
  "status": 400,
  "title": "Validation failed",
  "detail": "The request contains invalid fields.",
  "instance": "/api/companies",
  "errors": {
    "name": ["The name is required"],
    "website": ["The website must start with http:// or https://"]
  }
}
```

## 3. Lists: pagination, sorting, search, filters

### 3.1 Pagination

Paginated endpoints:

- `GET /api/companies`
- `GET /api/job-postings`
- `GET /api/companies/{companyId}/job-postings`
- `GET /api/applications`
- `GET /api/notes`

`GET /api/note-categories` is **not** paginated (section 10).

Response:

```ts
type Page<T> = {
  content: T[]
  page: number // 0-based index of the returned page
  size: number // effective page size (after the cap of 100)
  totalElements: number // number of matches across all pages
  totalPages: number // 0 when there are no matches
}
```

Query parameters:

| Parameter | Type   | Default | Behavior                                                                                                         |
| --------- | ------ | ------- | ---------------------------------------------------------------------------------------------------------------- |
| `page`    | int    | `0`     | **0-based.** Negative or non-numeric values fall back to `0`. A page beyond the last returns an empty `content`. |
| `size`    | int    | `15`    | Values above `100` are capped to `100`. Values below `1` or non-numeric values fall back to `15`.                |
| `sort`    | string | see 3.2 | See 3.2.                                                                                                         |

There is no unpaginated variant. To load all items (e.g. for a select box), request `size=100` and continue while `page < totalPages - 1`.

### 3.2 Sorting

Format: `sort=property` or `sort=property,asc|desc` (direction defaults to `asc`). Repeat the parameter for several keys; the first one has the highest priority.

```
GET /api/companies?sort=city,asc&sort=name,asc
GET /api/applications?sort=appliedAt,desc
```

| Endpoint                                      | Default sort     | Sort properties (contract)                                                                                             |
| --------------------------------------------- | ---------------- | ---------------------------------------------------------------------------------------------------------------------- |
| `GET /api/companies`                          | `name,asc`       | `name`, `city`, `postalCode`, `street`, `website`, `createdAt`, `updatedAt`                                            |
| `GET /api/job-postings`                       | `createdAt,desc` | `title`, `location`, `status`, `publishedAt`, `archivedAt`, `createdAt`, `updatedAt`, `company.name`                   |
| `GET /api/companies/{companyId}/job-postings` | `createdAt,desc` | same as `GET /api/job-postings`                                                                                        |
| `GET /api/applications`                       | `createdAt,desc` | `status`, `priority`, `appliedAt`, `closedAt`, `createdAt`, `updatedAt`, `jobPosting.title`, `jobPosting.company.name` |
| `GET /api/notes`                              | `createdAt,desc` | `title`, `createdAt`, `updatedAt`                                                                                      |

Rules:

- Sort properties are **entity property names**, not response field names. Computed or flattened response fields (`jobsCount`, `hasApplication`, `daysSinceApplication`, `companyName`, `jobTitle`, `noteCategory`, …) are not sortable.
- The frontend MUST use only the properties listed above. An unknown property returns `400 Invalid sort property`.
- The server always adds `id` as the final sort key, so paging is stable.
- Sorting is applied on the server across all pages. The frontend MUST NOT re-sort `content`.
- Enum properties (`status`, `priority`) sort **alphabetically by enum value** (e.g. `HIGH`, `LOW`, `MEDIUM`, `NONE`), not by workflow or importance.
- `null` values sort last with `asc` and first with `desc` (PostgreSQL default).

### 3.3 Search and filters

| Endpoint                                      | Search `q` matches (case-insensitive substring) | Filters                                         | Allowed combinations                                    |
| --------------------------------------------- | ----------------------------------------------- | ----------------------------------------------- | ------------------------------------------------------- |
| `GET /api/companies`                          | company name                                    | –                                               | –                                                       |
| `GET /api/job-postings`                       | posting title **or** company name               | `filter` (section 7.3)                          | `q` only with `filter=ALL`                              |
| `GET /api/companies/{companyId}/job-postings` | –                                               | –                                               | –                                                       |
| `GET /api/applications`                       | posting title **or** company name               | `status`, `priority` (section 8.3)              | `q` **or** filters; `status` + `priority` combine (AND) |
| `GET /api/notes`                              | note title **or** content                       | `noteCategoryId`, `applicationId` (section 9.3) | `q` **or** filters; both filters combine (AND)          |

Rules:

- `q` is optional. The server trims it; an empty or whitespace-only value means "no search".
- A non-empty `q` together with a filter returns `400 Invalid request combination`. The UI MUST treat search and filters as mutually exclusive (e.g. clear the filters when the user starts typing).
- Each filter parameter takes exactly one value.
- Query parameters not listed for an endpoint are ignored.
- When `q` or a filter changes, the frontend MUST reset `page` to `0`.

The frontend MUST always send the enum value, never a display label. Display labels MUST be defined in one central place.

## 6. Companies

### 6.1 Types

```ts
type CompanyCompact = {
  id: UUID
  name: string
  jobsCount: number // all job postings of the company, including archived ones
}

type CompanyDetail = {
  id: UUID
  name: string
  website: string | null
  street: string | null
  postalCode: string | null
  city: string | null
  jobsCount: number // all job postings of the company, including archived ones
}

// Embedded in JobPostingDetail and ApplicationDetail
type CompanySummary = {
  id: UUID
  name: string
  website: string | null
  street: string | null
  postalCode: string | null
  city: string | null
}

type CompanyRequest = {
  name: string
  website?: string | null
  street?: string | null
  postalCode?: string | null
  city?: string | null
}
```

### 6.2 Validation (`CompanyRequest`)

All string fields are trimmed by the server before validation.

| Field        | Rules                                                                             |
| ------------ | --------------------------------------------------------------------------------- |
| `name`       | required, not blank, max 255; unique (case-insensitive, after trimming)           |
| `website`    | optional; if set: must start with `http://` or `https://`, no whitespace, max 255 |
| `street`     | optional; if set: not blank, max 255                                              |
| `postalCode` | optional; if set: not blank, max 20                                               |
| `city`       | optional; if set: not blank, max 255                                              |

An optional field MUST be sent as `null` or omitted when empty. An empty or whitespace-only string is rejected with `400 Validation failed`.

### 6.3 Endpoints

- **`GET /api/companies`** – `Page<CompanyCompact>`; search by name with `q`; no filters.
- **`GET /api/companies/{id}`** – `CompanyDetail`.
- **`POST /api/companies`** – creates a company; returns `201 CompanyDetail` (`jobsCount` is `0`). Duplicate name → `409`.
- **`PUT /api/companies/{id}`** – **full replacement** of all editable fields; omitted optional fields become `null`. Duplicate name (another company) → `409`.

## 7. Job postings

### 7.1 Types

```ts
type JobPostingCompact = {
  id: UUID
  title: string
  companyName: string
  location: string | null
  hasApplication: boolean
  createdAt: LocalDateTime
  // status and archivedAt are intentionally not part of the list item
}

type JobPostingDetail = {
  id: UUID
  company: CompanySummary
  title: string
  description: string | null
  location: string | null
  url: string
  status: JobPostingStatus
  applicationId: UUID | null // null = no application exists for this posting
  publishedAt: LocalDate | null
  createdAt: LocalDateTime
  archivedAt: LocalDate | null // null = not archived
}

// Embedded in ApplicationDetail
type JobPostingSummary = {
  id: UUID
  title: string
  description: string | null
  location: string | null
  url: string
  status: JobPostingStatus
  publishedAt: LocalDate | null
  archivedAt: LocalDate | null
}

type JobPostingRequest = {
  title: string
  description?: string | null
  location?: string | null
  url: string
  status: JobPostingStatus
  publishedAt?: LocalDate | null
}

type JobPostingArchiveRequest = {
  archived: boolean
}
```

### 7.2 Validation (`JobPostingRequest`)

`title`, `location` and `url` are trimmed by the server before validation. `description` is stored as sent.

| Field         | Rules                                                                      |
| ------------- | -------------------------------------------------------------------------- |
| `title`       | required, not blank, max 255                                               |
| `description` | optional, no length limit                                                  |
| `location`    | optional; if set: not blank, max 255                                       |
| `url`         | required, must start with `http://` or `https://`, no whitespace, max 1000 |
| `status`      | required                                                                   |
| `publishedAt` | optional; must not be in the future                                        |

`JobPostingArchiveRequest.archived` is required (`400 Validation failed` if missing).

### 7.3 `GET /api/job-postings` – `filter`

Optional, default `ALL`, one value per request.

| `filter`   | Returns                                                                                                   |
| ---------- | --------------------------------------------------------------------------------------------------------- |
| `ALL`      | all postings, including archived ones. The only value that can be combined with `q`.                      |
| `INACTIVE` | `status = INACTIVE` – archived or not, with or without application                                        |
| `ARCHIVED` | `archivedAt != null` – any status                                                                         |
| `OPEN`     | postings that can still be applied to: `status = ACTIVE` **and** not archived **and** without application |
| `APPLIED`  | postings with an application (never archived)                                                             |

A posting that is inactive or archived and has no application appears in neither `OPEN` nor `APPLIED`.

`GET /api/companies/{companyId}/job-postings` has no `filter` and no `q`; it always returns all postings of the company, including archived ones. An unknown company returns `404`.

### 7.4 Endpoints

- **`POST /api/companies/{companyId}/job-postings`** – creates a posting for the company; returns `201 JobPostingDetail` (`applicationId` and `archivedAt` are `null`). Unknown company → `404`.
- **`PUT /api/job-postings/{id}`** – **full replacement** of all fields in `JobPostingRequest`; omitted optional fields become `null`. It does not change the company, the archive state or the application.
- **`PATCH /api/job-postings/{id}/archive`**
  - `{ "archived": true }` archives the posting (`archivedAt` = today).
  - `{ "archived": false }` restores it (`archivedAt` = `null`).
  - `409` when archiving an already archived posting, restoring a posting that is not archived, or archiving a posting that has an application.

### 7.5 Rules

- Archive state (`archivedAt`) and `status` (`ACTIVE`/`INACTIVE`) are independent. The frontend MUST NOT infer one from the other.
- `JobPostingCompact` exposes neither `status` nor `archivedAt`. In a list, the archive state is only known when the list was loaded with `filter=ARCHIVED`.
- "Has an application" is `hasApplication` in the list and `applicationId != null` in the detail.

UI actions on the posting detail:

| State                                         | Offer                                         |
| --------------------------------------------- | --------------------------------------------- |
| `archivedAt != null`                          | badge "archived" + restore                    |
| `archivedAt == null && applicationId == null` | start application + archive                   |
| `applicationId != null`                       | link to the application; no archive, no start |

## 8. Applications

### 8.1 Types

```ts
type ApplicationCompact = {
  id: UUID
  jobTitle: string
  companyName: string
  status: ApplicationStatus
  priority: ApplicationPriority
  appliedAt: LocalDate | null
  daysSinceApplication: number | null // days between appliedAt and today (server date); null when appliedAt is null
}

type ApplicationDetail = {
  id: UUID
  jobPosting: JobPostingSummary
  company: CompanySummary
  status: ApplicationStatus
  priority: ApplicationPriority
  appliedAt: LocalDate | null
  appliedVia: ApplicationChannel | null
  portalUrl: string | null
  closedAt: LocalDate | null
  createdAt: LocalDateTime
}

type ApplicationPatch = {
  status?: ApplicationStatus
  priority?: ApplicationPriority
  appliedVia?: ApplicationChannel
  portalUrl?: string // trimmed; must start with http:// or https://, no whitespace, max 1000
}
```

`appliedAt` and `closedAt` are managed by the server only (section 8.6).

### 8.2 Lifecycle

- Each job posting has **at most one** application.
- `POST /api/job-postings/{jobPostingId}/applications` creates it. The request has **no body**. The new application has `status = IN_PROGRESS`, `priority = NONE` and all other optional fields `null`.
- Errors: unknown posting → `404`; posting already has an application → `409`; posting is archived → `409`. On `409` the frontend MUST reload the posting detail instead of retrying.

### 8.3 `GET /api/applications` – filters

| Parameter  | Type                  | Effect                                       |
| ---------- | --------------------- | -------------------------------------------- |
| `status`   | `ApplicationStatus`   | only applications with exactly this status   |
| `priority` | `ApplicationPriority` | only applications with exactly this priority |

- Both are optional and combine with AND. Neither can be combined with `q`.
- There is no "all open" / "all closed" filter. Request one status at a time or group on the client.

### 8.4 `PATCH /api/applications/{id}`

- Partial update: only fields that are present **and non-null** are applied. `null` never clears a field.
- `appliedVia` and `portalUrl` can only be cleared by changing the status to `IN_PROGRESS`.
- The request is atomic: if the status transition is rejected (`409`), no other field of the same request is saved either.
- An empty body `{}` is valid and returns the unchanged application.
- Returns the updated `ApplicationDetail`.

### 8.5 Allowed status transitions

| Current status    | Allowed target statuses                                                                |
| ----------------- | -------------------------------------------------------------------------------------- |
| `IN_PROGRESS`     | `APPLIED`, `WITHDRAWN`                                                                 |
| `APPLIED`         | `IN_PROGRESS`, `WAITING`, `INTERVIEW`, `OFFER`, `REJECTED`, `NO_RESPONSE`, `WITHDRAWN` |
| `WAITING`         | `IN_PROGRESS`, `APPLIED`, `INTERVIEW`, `OFFER`, `REJECTED`, `NO_RESPONSE`, `WITHDRAWN` |
| `INTERVIEW`       | `IN_PROGRESS`, `APPLIED`, `WAITING`, `OFFER`, `REJECTED`, `NO_RESPONSE`, `WITHDRAWN`   |
| `OFFER`           | `IN_PROGRESS`, `APPLIED`, `WAITING`, `INTERVIEW`, `OFFER_ACCEPTED`, `OFFER_REJECTED`   |
| any closed status | `IN_PROGRESS`, `APPLIED`, `WAITING`, `INTERVIEW`, `OFFER`                              |

Any other transition, including setting the current status again, returns `409`. The UI MUST offer only the allowed targets.

### 8.6 Side effects of a status change

| New status      | Effect                                                                             |
| --------------- | ---------------------------------------------------------------------------------- |
| `APPLIED`       | `appliedAt` = today, if it was `null`                                              |
| `IN_PROGRESS`   | `appliedAt`, `appliedVia`, `portalUrl` → `null` (even if sent in the same request) |
| a closed status | `closedAt` = today, if it was `null`                                               |
| an open status  | `closedAt` → `null`                                                                |

After a PATCH the frontend SHOULD update its state from the response. If the current list is filtered by `status` or `priority`, the changed item may no longer match – reload the current page.

## 9. Notes

Notes are an independent resource. A note either stands on its own or is assigned to **at most one** application. A note can have **at most one** category.

### 9.1 Types

```ts
type NoteCompact = {
  id: UUID
  noteCategory: string | null // category NAME, not ID
  title: string
  createdAt: LocalDateTime
  updatedAt: LocalDateTime
  applicationId: UUID | null // null = not assigned to an application
  jobTitle: string | null // job title of the assigned application; null when unassigned
  companyName: string | null // company of the assigned application; null when unassigned
}

type NoteDetail = {
  id: UUID
  noteCategory: string | null // category NAME, not ID
  title: string
  content: string | null
  createdAt: LocalDateTime
  updatedAt: LocalDateTime
  applicationId: UUID | null
  jobTitle: string | null
  companyName: string | null
}

type NoteRequest = {
  applicationId?: UUID | null // null/omitted = not assigned
  noteCategoryId?: UUID | null // null/omitted = no category
  title: string
  content?: string | null
}
```

### 9.2 Validation (`NoteRequest`)

| Field            | Rules                                                     |
| ---------------- | --------------------------------------------------------- |
| `title`          | required, trimmed, not blank, max 255                     |
| `content`        | optional, no length limit, stored as sent                 |
| `applicationId`  | optional; if set, the application must exist (else `404`) |
| `noteCategoryId` | optional; if set, the category must exist (else `404`)    |

### 9.3 `GET /api/notes` – filters

| Parameter        | Type   | Effect                                  |
| ---------------- | ------ | --------------------------------------- |
| `noteCategoryId` | `UUID` | only notes of this category             |
| `applicationId`  | `UUID` | only notes assigned to this application |

- Both are optional and combine with AND. Neither can be combined with `q`.
- An unknown ID does **not** return `404`; the result is an empty page.
- There is no filter for "unassigned notes" or "notes without category".
- Notes of one application (e.g. on the application detail page): `GET /api/notes?applicationId={id}`.

### 9.4 Endpoints

- **`POST /api/notes`** – creates a note; returns `201 NoteDetail`.
- **`PUT /api/notes/{id}`** – **full replacement**: `title`, `content`, `applicationId` and `noteCategoryId` are all overwritten. Omitting `applicationId` or `noteCategoryId` **removes** the assignment or category. When editing, the frontend MUST send the current values again.
- **`DELETE /api/notes/{id}`** – deletes the note permanently; `204`.

### 9.5 Rules

- Responses contain the category **name** (`noteCategory`); requests take the category **ID** (`noteCategoryId`). To preselect the category in an edit form, resolve the ID by name from `GET /api/note-categories`.
- `jobTitle` and `companyName` are read-only display fields and are never sent.
- The `updatedAt` value in the `PUT` response may still show the previous value. Use `GET /api/notes/{id}` when the exact value is required.

## 10. Note categories

### 10.1 Types

type NoteCategory = {

type NoteCategoryRequest = {

### 10.2 Endpoints and rules

- **`GET /api/note-categories`** – returns all categories as a plain array (not paginated), **sorted by name ascending**.
- **`POST /api/note-categories`** / **`PUT /api/note-categories/{id}`** – duplicate name → `409`.
- **`DELETE /api/note-categories/{id}`** – deletes the category. Its notes are kept; their `noteCategory` becomes `null`.

## 11. Frontend implementation rules

1. Use only the endpoints, fields, query parameters and enum values in this document. Do not invent anything.
2. Keep all API access in a dedicated client layer. Parse `ApiProblem` centrally there.
3. Handle errors by `status` and `title`:

   | Case                                     | Handling                                               |
   | ---------------------------------------- | ------------------------------------------------------ |
   | `400 Validation failed`                  | show `errors[field]` on the matching form fields       |
   | `400 Invalid sort property` (list)       | reset sort to the default and reload                   |
   | `400 Invalid request combination` (list) | client bug – clear filters, keep `q`, reload           |
   | `400 Bad Request`                        | client bug – show a generic error                      |
   | `404 Resource not found`                 | show a not-found state, or reload the affected data    |
   | `404 Not Found`, `405`, `415`            | client bug – show a generic error                      |
   | `409 Conflict`                           | show `detail` to the user and reload the affected data |
   | `500`                                    | show a generic error and offer a retry                 |

4. Never discard unsaved user input on an error.
5. List, detail, summary and request types differ. Model each separately and handle every nullable field.
6. Keep enum-to-label mappings (section 4) in one place.
7. After a mutation, update state from the returned resource or reload the affected list page or detail.
8. Paginated lists: model `Page<T>` generically; keep `page`, `size`, `sort`, `q` and filters as list state (ideally in the URL); `page` is 0-based. If a page becomes empty after a mutation and `page > 0`, load the previous page.
9. Never re-sort a paginated `content` array on the client.
10. Notes assigned to an application link to it via `applicationId` and display `jobTitle` / `companyName`.
11. For `PUT` endpoints (companies, job postings, notes) always send the complete resource, including unchanged optional fields.

## 12. Known limitations

These describe current behavior. The frontend MUST NOT build workarounds that depend on them, but SHOULD be aware of them.

| Area             | Behavior                                                                                                                                                                                             |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Search wildcards | In `q` for job postings, applications and notes, `%` and `_` act as SQL wildcards (e.g. `q=_` matches everything). Company search treats them literally.                                             |
| Sorting notes    | Only the flat properties in section 3.2 are supported. Nested properties (e.g. `noteCategory.name`) are accepted by the server but can drop notes without a category or application from the result. |
| Delete           | Companies, job postings and applications cannot be deleted.                                                                                                                                          |
| Authentication   | None; the API is not multi-user capable yet.                                                                                                                                                         |
